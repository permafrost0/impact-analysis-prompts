# 使い方ガイド

あなたが話す相手は **`impact-orchestrator`** だけです。あなたが書くのは、基本的に次の5種類です。

| 場面 | 書くこと |
|---|---|
| 始める | 「新しい調査を始めたい」と、シート名・追加開発の部分の見分け方 |
| 承認する | 「承認」、または確認事項への答え(「Q1: はい / Q3: ハイフンあり」) |
| 直してもらう | 直してほしい点を具体的に(「F-02 の要件に、確認画面の表示も入れて」) |
| 方針を決める | 「今後は〜」「この設計書では、青字は対象外」 |
| 再開する | 「{調査ID} の続きをやりたい」 |

---

## 1. 準備

### 1-1. 必要なもの
- VS Code と GitHub Copilot(Copilot Chat で、カスタムエージェントとエージェントモードが使えること)
- Python 3.8 以上
  - Excel を読むライブラリ(openpyxl)と YAML を読むライブラリ(pyyaml)は、足りなければ調査の開始時にオーケストレータが入れます。Python 本体だけは事前に入れておいてください。

### 1-2. このフォルダを用意する
- このフォルダ一式は、セットアップ用ファイル(`impact-analysis-setup.md`。このフォルダとは別に配布)1つから展開できます。受け取った場合は、そのファイルの冒頭の「使い方」に従って展開します。
- 展開したら、VS Code でこのフォルダを開き、コマンドパレットの「Developer: Reload Window」で再読み込みします。

### 1-3. ワークスペース
エージェントが対象のソースを読めるよう、**このフォルダと対象のソースを1つのワークスペースに入れます**。

1. VS Code でこのフォルダを開く
2. 「ファイル > フォルダーをワークスペースに追加」で、対象のソースのフォルダを加える
3. 「ファイル > 名前を付けてワークスペースを保存」で保存しておくと、次回から同じ構成で開けます

### 1-4. 設計書を置く

| フォルダ | 置くもの | 読まれ方 |
|---|---|---|
| `input/target/` | 今回の**追加開発の設計書**(追加・変更が書き込まれた最新版) | 指示したシートだけが Markdown に変換され、そのうち対象の行と見出し行が読まれます |
| `input/reference/` | 追加開発の設計書から「既存の○○設計書を参照」と参照されている**既存の設計書**(あれば) | 必要なときに、フェーズ1で**見出しの一覧だけ**が読まれます。本文は読まれません |

- 数式を使っている設計書は、Excel で開いて保存した状態のものを置いてください(計算結果が保存されていないと、値を読めません。読めないセルは「計算結果なし」と表示されます)。
- **調査の途中で、設計書とソースを変更しないでください。** 調査の開始時に状態を記録し、各フェーズの最後に変わっていないことを確かめます。変わっていると、調査は止まります(→ 7章)。
  - 設計書を Excel で開いて見るのは構いません(開いている間にできる `~$` の一時ファイルは照合から外しています)。保存はしないでください。
  - IDE やビルドが自動で作るもの(`target`、`bin`、`.settings`、`.classpath` など)も照合から外しています。

### 1-5. 設計書から読み取るもの

| 読み取るもの | 読み取らないもの |
|---|---|
| セルの値(結合セルは範囲で1回) | 画像、グラフ、コネクタ(線・矢印)、埋め込みオブジェクトの中身 |
| 文字色・背景色・取り消し線(セル内の一部だけの書式も) | |
| コメント(メモ)、ハイパーリンク | |
| 数式(式と計算結果)、表示形式(先頭のゼロなど) | |
| 入力規則(プルダウンの選択肢) | |
| 図形・テキストボックスの文字と、近くの行番号 | |
| 非表示の行・列・シート(非表示であることも記録) | |

読み取らないものがシートにある場合は、変換結果の「注意」の節に書かれます。図にしか書かれていない仕様がある場合は、その内容を文字で伝えてください。

### 1-6. エージェントを選ぶ
Copilot Chat を開き、エージェントの選択で **`impact-orchestrator`** を選びます。
他のエージェントはオーケストレータ専用なので、選択肢には出ません。

### 1-7. ターミナルの実行の確認
調査中、オーケストレータとエージェントは次のコマンドを実行します。実行の前に確認が出たら、内容を見て許可してください。

- `python --version`、`python -c "import openpyxl, yaml"`、`pip install openpyxl pyyaml`(環境の確認)
- `python tools/〜.py …`(変換・点検・資料の作成など)

**これ以外のコマンド(ビルド、テスト、git、ファイルの削除など)は、決まりで禁止しています。** 確認が出たら、許可しないでください。

## 2. 調査を始める

### 2-1. 最初のメッセージ

```
新しい調査を始めたい。
名前: ユーザー登録への電話番号認証の追加
ソース: C:\work\app
設計書: input/target/機能設計書_ユーザー登録.xlsx
シート: 画面項目定義、イベント一覧、処理仕様、メッセージ一覧
見分け方: 変更は赤字、削除は取り消し線
参照用: input/reference/会員管理設計書.xlsx を置いた
```

「新しい調査を始めたい」だけでも構いません。足りないものは、オーケストレータが聞きます。

### 2-2. シートの指定
- 読まれるのは、**指示したシートだけ**です。指示しなかったシートは変換も読み取りもされません。
- シート名が違っていたら、オーケストレータが設計書のシート名の一覧から近いものを示して確かめます。
- すべてのシートが対象のときは「全シート」と伝えます。

### 2-3. 追加開発の部分の見分け方

| 見分け方 | 例 | 向いている場面 |
|---|---|---|
| 書式の目印 | 「変更は赤字」「削除は取り消し線」「追加は黄色の背景」 | 設計書の書き方に決まりがある |
| 名前 | 「イベント一覧の『電話番号認証ボタン押下』を追加」「メッセージ一覧の MSG-E020〜E022 を追加」 | 目印がない、一部だけが対象 |
| シート全体 | 「メッセージ一覧は全部が新規」 | 新しく作ったシート |
| 識別文字列 | 「変更履歴の列が 2026/10 の行」 | 版の印がある |
| 行範囲 | 「画面項目定義の 25〜31 行」 | 最後の手段 |

- 既存の定義を書き換えた・削除した場合は、「〜を変更」「〜を削除」と添えると確実です。
- 「赤字は変更」のような**いつも同じ決まり**は、方針に登録できます(5章)。登録すると、次からはシート名を伝えるだけで足ります。

## 3. 各フェーズで起きること

### 3-1. フェーズ1 要件の抽出

1. **範囲の特定**(p1a): あなたの指示が、シートの何行目に当たるかを特定します。
2. **途中の点検**(p1-scope): レビュー担当が、範囲が指示どおりかを確かめます。
3. **範囲について途中で質問が来るのは、ここだけです。** 指示に当たる行が見つからない・候補が複数ある、または対象の行が指示していないシートを参照している(例:「外部IF定義シート参照」)場合です。抽出が無駄にならないよう、先に確かめます。
   (このほかにフェーズの途中で質問が来るのは、不合格や点検のエラーが2回直しても解消しないとき、承認済みのフェーズに誤りが見つかったとき、ソースや設計書の変更を検知したとき、環境の問題があるときだけです)
4. **要件の抽出**(p1b): シートごとに並列で、対象の行から要件を取り出し、新規・変更・削除・既存の流用に分けます。
   - 「必要に応じて」「従来どおり」など、判断に困る表現は要件にせず、原文を引用して確認事項にします。
   - 今回変わらない既存の説明は、要件にしません。
   - 「既存の○○と同様」は「既存の流用」とし、中身はフェーズ2でコードから調べます。行の言葉だけでは既存の機能を特定できず、既存設計書の参照が明記されている場合に限り、参照先の見出しだけを読んで機能名を突き止めます。
5. **機能ごとの統合**(p1c): 要件を、利用者から見た機能(F-01 など)にまとめます。この機能が、フェーズ2・3と承認資料の単位になります。
6. **点検**(p1) → **承認**: `01_requirements/requirements.md`

承認資料の並び:
```
はじめに(レビュー担当の要約)
1. 抽出した要件(機能ごと)
   機能の一覧
   F-01 … 要件 / 区分 / 内容 / 主な値 / 設計書の箇所 / 確認
   F-02 …
   要件にしなかった記述(判断に困る表現、既存の説明)
   範囲の特定(指示 → 設計書の行)
   参照先の設計書(既存)の扱い
2. 確認事項(Q1, Q2, …)
付録(レビュー担当の点検、仮定と課題の一覧)
```

### 3-2. フェーズ2 懸念事項の抽出

1. **流用先の特定**(p2a)と**修正箇所の特定**(p2b、機能ごと)を並列に行います。修正箇所は、画面から Controller → Form → Service → Repository/Mapper → SQL と、実際にコードを辿って決めます。
2. **途中の点検**(p2-changes): 「今の振る舞い」がコードどおりか、修正の漏れ、共通処理の判定漏れを確かめます。
3. **影響**(p2c)・**共通処理の判断**(p2d)・**懸念**(p2e)を並列に調べます。
   - 影響 = 今回の修正で、**既存の機能**がどう変わりうるか(影響がなかった修正も、調べた範囲を残します)
   - 共通処理 = 他の機能からも使われる処理を直すとき、全体修正にするか部分修正にするか(呼び出し元を1件ずつ確かめます)
   - 懸念 = 今回の機能を**作るうえで**の危うさ(トランザクション、既存データ、二重送信など)
4. **点検**(p2) → **承認**: `02_impact/impact_report.md`(影響調査報告書)

承認資料の並び:
```
はじめに
1. 抽出した内容(機能ごと)
   機能の一覧(修正・影響・懸念の件数)
   F-01
     (1) 今の処理の流れ(コードから)
     (2) 修正箇所(ファイル:行、今の振る舞い → 変更後、コードの抜粋)
     (3) 流用する既存処理
     (4) 既存機能への影響(重大度つき)
     (5) 実装上の懸念(重要度・推奨する対応つき)
     (6) 調べた範囲
   機能をまたぐ事項(共通処理の判断と呼び出し元の一覧など)
2. 確認事項
付録(回帰テストの観点、点検結果、仮定と課題)
```

### 3-3. フェーズ3 実装計画

1. **順番**(p3a): 機能を作る順番を決めます。まず依存関係(使われる側が先)、そのうえで
   `削除 → 既存の流用 → 既存を手本に追加 → 既存の振る舞いを変える → 新しい仕組み → 共通処理・高リスク`
   の順です。既存をもとにしたものから進め、慎重さが要るものを後ろにします。順番を崩すときは理由が書かれ、確認事項になります。
2. **手順**(p3b、機能ごと)と**確認方法**(p3c)を並列に作ります。
3. **点検**(p3) → **承認**: `03_plan/implementation_plan.md`(実装計画書)

承認資料の並び:
```
はじめに
1. 実装計画(機能ごと)
   実装の順番(順番 / 機能 / 進め方 / 理由)
   F-01
     (1) ゴールと前提
     (2) 作業手順(ファイル・場所・直す行・やること・修正の ID)
         手順ごとに、直す場所の今のコードと、手本にする既存コードの抜粋
     (3) 新しく作るもの(名前・置き場所と、その根拠)
     (4) 合わせる書き方(周辺のコードから)
     (5) 守るべき既存の振る舞い
     (6) 確認方法(新規の確認と回帰の確認)
     (7) 完了条件
2. 確認事項
付録(修正箇所と手順の対応、点検結果、仮定と課題)
```

この実装計画書が、製造工程の入力です。

### 3-4. 振り返り(フェーズ3の承認の後、毎回)

今回の調査で起きたこと(あなたの修正、差し戻し、レビュー担当の不合格、外れた仮定、何度も出る確認事項)と、過去の記録(`history/feedback_log.md`、`history/questions_log.md`)から、次回のための方針の改善案を作ります。

```
開くファイル: work/runs/{調査ID}/retrospective.md

振り返りが終わりました。方針の改善案が 2 件あります。

P1: policies/common.md に追加「設計書に電話番号の形式の記載がない場合は、ハイフンなしの数字として扱う」
P2: policies/review.md に追加「【p1】処理仕様の『既存設計を参照』が、既存の流用として拾われているか」

改善案ごとに「P1: 採用 / P2: 不採用」の形で答えてください。答えなかった改善案は採用しません。
```

採用したものだけが、次の調査から使われます。**答えなかった改善案は採用されません**(確認事項とは扱いが逆なので注意してください)。改善案がなければ「今回は改善案はありません」と伝えられます。

## 4. 答え方

フェーズが終わると、次の形で承認を求められます。1行目は、いつも開くファイルです。

```
開くファイル: work/runs/20261007-usertel/02_impact/impact_report.md

フェーズ2(懸念事項の抽出)が終わりました。レビュー担当の点検: 条件付き合格
15か所の修正(うち共通処理1)を特定しました。既存機能への影響は2件(高1・中1)、懸念は2件(高1・中1)です。

確認事項が 2 件あります(資料の「2. 確認事項」)。
番号を付けて答えてください。例:「Q1: はい / Q2: ハイフンあり」
答えなかった確認事項は、資料に書かれている内容のまま確定します。
内容に問題がなければ「承認」、直してほしい点があれば具体的に伝えてください。
```

### 4-1. 確認事項への答え
- 番号を付けて答えます。「Q1: はい / Q2: ハイフンありが正しい / Q4: 要件にする」
- **答えなかった確認事項は、資料に書かれた内容のまま確定**します。確認事項には「今どう扱っているか」が必ず書かれているので、そのままでよければ答える必要はありません。
- 確認事項がすべて資料のままでよく、直す点もなければ「承認」だけで構いません。

### 4-2. 直してほしいとき
- 自由に書いて構いません。機能 ID(F-01)・要件 ID(REQ-S1-003)・修正の ID(CHG-F01-002)などを添えると確実です。
  - 「F-02 と F-03 は1つの機能にまとめて」
  - 「REQ-S2-004 は今回の対象外」
  - 「CHG-F01-003 は Service ではなく Validator に入れる」
- オーケストレータが、担当のエージェントに直させ、点検をやり直してから、もう一度承認を求めます。その際、何が変わったかが一言添えられます。
- あなたの判断は `decisions.yaml` に記録され、後のフェーズの全エージェントが従います。

### 4-3. 前のフェーズに戻りたいとき
「フェーズ1の F-02 の要件を直したい」のように伝えます。そのフェーズからやり直し、後のフェーズも作り直します。

## 5. 方針を登録する

方針(`policies/`)は、次の調査からも全エージェントが従う決まりです。エージェント定義の手順より優先されます。

| 方針のファイル | 書かれること |
|---|---|
| `policies/common.md` | 設計書の書き方の決まり(「赤字は変更」など)、全フェーズに共通の決まり |
| `policies/phase1.md`〜`phase3.md` | 各フェーズの作業の決まり |
| `policies/review.md` | レビュー担当が追加で確かめること |
| `policies/CHANGELOG.md` | 方針の変更の履歴 |

方針が登録されるのは、次の2つの場合です。
- 振り返りの改善案を、あなたが採用したとき
- 調査中に「今後は」「毎回」など、今回限りではない決まりをあなたが話したとき(登録するか、文案つきで聞かれます)

方針は、オーケストレータが追記・書き直し・廃止します。ファイルを直接編集しても構いませんが、その場合は `policies/CHANGELOG.md` にも1行書いてください。
ソースを変更させる、根拠を省かせる、点検を省かせる、といった方針は登録できません。

---

## 6. 中断と再開

- 調査の進み具合は `work/runs/{調査ID}/state.yaml` に記録されています。
- 再開するときは、新しいチャットで `impact-orchestrator` を選び、「{調査ID} の続きをやりたい」と伝えます。今のフェーズと状態が一言で示され、続きから進みます。
- 調査ID が分からなければ、`work/runs/` のフォルダ名を見てください。

## 7. 困ったとき

| 状況 | どうするか |
|---|---|
| エージェントの選択に `impact-orchestrator` が出ない | このフォルダ(`.github/agents/` があるフォルダ)を VS Code で開いているか確かめ、「Developer: Reload Window」で再読み込みします。それでも出ない場合は、VS Code と Copilot の拡張機能を新しくします |
| Python がないと言われた | Python を入れてから、もう一度始めます |
| シート名が見つからないと言われた | 示された一覧から、正しいシート名を答えます |
| 「ソースや設計書が変わりました」と言われて止まった | 調査中に、誰かがファイルを変更したか、git の操作でファイルが入れ替わっています。示されたファイルを元に戻して「続けて」と伝えるか、新しい調査として始め直します |
| 承認資料のコードの抜粋に「抜粋できません」と出る | ソースのルートの指定が違う可能性があります。オーケストレータにソースのルートを確かめるよう伝えます |
| 並列に動いていないように見える | 同時に呼び出せない環境では、1つずつ順に動きます。結果は同じで、時間だけが変わります |
| 時間がかかる | 指示するシートを、本当に必要なものに絞ります。見分け方の決まりを方針に登録しておくと、範囲の特定が速く確実になります |
| レビュー担当の不合格が続いていると言われた | 示された指摘の内容を見て、どう扱うかを答えます(例:「その点は確認事項にして進めて」) |

## 8. 調査フォルダの中身

```
work/runs/{調査ID}/
├─ state.yaml                     進み具合
├─ scope.yaml                     あなたの指示(原文のまま)
├─ decisions.yaml                 あなたの判断
├─ guard/baseline.json            ソースと設計書の状態の記録
├─ 01_requirements/
│  ├─ sheets/                     指示したシートの変換結果
│  ├─ scope_resolution.yaml       範囲の特定
│  ├─ extract/                    シートごとの要件
│  ├─ requirements.yaml           要件の正本
│  └─ requirements.md             ★フェーズ1の承認資料
├─ 02_impact/
│  ├─ reuse.yaml / changes/ / impacts.yaml / common_components.yaml / concerns.yaml
│  └─ impact_report.md            ★影響調査報告書(フェーズ2の承認資料)
├─ 03_plan/
│  ├─ plan.yaml / steps/ / verification.yaml
│  └─ implementation_plan.md      ★実装計画書(フェーズ3の承認資料)
├─ review/                        レビュー担当の点検結果と、確認事項の番号の対応
├─ retrospective.yaml

```

`.yaml` はエージェント同士がやり取りする正本、`.md` はスクリプトが `.yaml` から作る資料です。`.md` を手で直しても、作り直すと消えます。直したい点はオーケストレータに伝えてください。

`history/` には、調査ごとの記録(`runs.md`)、差し戻し・修正・不合格の記録(`feedback_log.md`)、確認事項とあなたの答えの記録(`questions_log.md`)がたまります。振り返りで、繰り返し起きていることを見つけるのに使われます(調査そのものには使われません)。`input/`・`work/runs/`・`history/` の中身は、各自の PC の中だけで使います(git の管理対象外です)。

# 使い方ガイド

あなたが話す相手は `impact-orchestrator` だけです。オーケストレータが承認フローに沿って、各フェーズのエージェントとレビュー担当を呼び出します。

あなたが書くのは、基本的に次の4種類です。

| 場面 | 書くこと |
|---|---|
| 開始 | 「新しい調査を始めたい」と、追加開発になった部分(シート名・イベント名・書式の目印などで) |
| 承認 | 「OK」「次へ」 |
| 差し戻し | 「差し戻し」+ 理由(承認の観点の番号やIDを添えると確実) |
| 方針の変更 | 「今後は〜して」「フェーズNの方針を〜に変えて」「この設計書では赤字が変更箇所」 |

---

## 1. 準備

### 必要なもの
- VS Code と GitHub Copilot(Copilot Chat が使えること)
- Python(3.8以上)

設計書のExcelは、フェーズ0でリポジトリ同梱の変換スクリプト(`tools/design_to_json.py`)が JSON と Markdown に変換します。同じ設計書からは毎回まったく同じ結果になるので、調査の根拠の行番号がずれません。変換に使うライブラリ(openpyxl)はエージェントが確認し、無ければ自分でインストールします。Python 本体だけは事前に入れておいてください。

### ワークスペース
エージェントが対象ソースを読めるよう、**このリポジトリと対象ソースを1つのワークスペースに入れます**。

1. このリポジトリをクローンし、VS Code で開く
2. メニューの「ファイル > フォルダーをワークスペースに追加」で、対象ソースのフォルダを追加する
3. 「ファイル > 名前を付けてワークスペースを保存」で保存しておくと、次回から同じ構成で開ける

### 設計書を置く
機能設計書・DB設計書のExcelを、このリポジトリの `input/` フォルダに置きます。

- 設計書は、追加開発の内容が追記された最新版を置いてください
- 調査を始めると、その時点の設計書がランのフォルダ(`work/runs/{run_id}/00_scope/original/`)にコピーされ、以降はそのコピーを根拠に調査します。調査の途中で `input/` の設計書を差し替えても、進行中の調査には影響しません

### 設計書から取り込まれるもの
| 取り込まれるもの | 取り込まれないもの |
|---|---|
| セルの値(結合セルは展開) | 画像の中に描かれた文字・図(画像ファイルとして渡され、必要ならエージェントが目で確認) |
| 図形・テキストボックス・グループ図形の文字と位置 | 埋め込みオブジェクト(他のExcel・Word・PDFなど)の中身 |
| 取り消し線・文字色・背景色(セル内の一部だけの書式も) | スレッド形式のコメントの返信 |
| コメント(メモ)、ハイパーリンク | |
| 数式(式と計算結果)、表示形式(先頭ゼロなど) | |
| 入力規則(プルダウンの選択肢) | |
| 非表示のシート・行・列(非表示であることも記録) | |

取り込まれないものは、変換結果の `index.md` の「取り込めなかった情報」に一覧され、課題として承認時に確認を求められます。
数式を使っている場合は、Excel で開いて保存した状態のファイルを置いてください(計算結果が保存されていないと値を読めません)。

### エージェントを選ぶ
1. Copilot Chat を開く
2. チャット入力欄のエージェント選択から `impact-orchestrator` を選ぶ

各フェーズのエージェントとレビュー担当はオーケストレータ専用なので、選択肢には表示されません。

### ターミナル実行の確認
フェーズ0では、設計書のコピー、ライブラリの準備、設計書の変換、名前での検索のためにターミナルでコマンドを実行します。実行前に確認が表示されたら、内容を見て許可してください。

## 2. 調査を始める

### 追加開発の部分の指示のしかた
追加開発になった部分は、**シート名・イベント名・項目名などの名前、または書式の目印で**指示します。行番号を調べる必要はありません。設計書のどの行に当たるかはエージェントが調べ、確認のために表で見せてくれます。

| 指示したいもの | 書き方の例 |
|---|---|
| シート全体 | 「ユーザー登録画面のメッセージ一覧シートすべて」 |
| 画面項目 | 「画面項目定義の『電話番号』『認証コード』を追加」 |
| イベント | 「イベント一覧の『電話番号認証ボタン押下』を追加」 |
| 処理 | 「処理仕様の『3.2 電話番号認証処理』を追加」 |
| メッセージ | 「メッセージ一覧の MSG-E020〜E022 を追加」 |
| 設定 | 「設定ファイルの sms.timeout を追加」 |
| テーブル・カラム | 「DB設計書の M_USER に TEL と TEL_VERIFIED を追加」 |
| 書式の目印 | 「画面項目定義の赤字の行が今回の変更」「取り消し線の行は削除」 |
| 識別文字列 | 「変更履歴列が 2026/10 の行すべて」 |
| 行範囲(最終手段) | 「画面項目定義の25〜31行」 |

既存の定義を書き換えた場合や削除した場合は、「〜を変更」「〜を削除」と書いてください。

### 開始のメッセージの例

```
新しい調査を始めたい。
機能名: ユーザー登録への電話番号認証の追加
設計書: input/ の 機能設計書_ユーザー登録.xlsx と DB設計書.xlsx
対象ソース: C:\work\app
追加開発の部分:
- ユーザー登録画面の画面項目定義の赤字の行
- イベント一覧の『電話番号認証ボタン押下』を追加
- 処理仕様の『3.2 電話番号認証処理』を追加
- メッセージ一覧の MSG-E020〜E022 を追加
- DB設計書の M_USER に TEL と TEL_VERIFIED を追加
```

「新しい調査を始めたい」だけでも構いません。足りない情報はオーケストレータが聞いてきます。

## 3. フェーズの流れ

| フェーズ | 内容 | 並列 |
|---|---|---|
| 0 スコープ確定 | 設計書を変換し、指示を設計書の行・図形に解決する | |
| 1 読解 | 要件の抽出、ソースの構成と規約・設計方針の読み取り、入口の特定 | 3つ並列 |
| 2 変更箇所特定 | 要件と入口を突き合わせ、変更内容と従う規約を決め、共通処理かを判定する | |
| 3 影響範囲 | 既存機能への影響を調べ、共通処理を全体修正にするか部分修正にするかを判断する | 2つ並列 |
| 4 製造への引き継ぎ | 製造タスク、タスク指示書、テスト仕様、コーディングガイドを作る | 一部並列 |

各フェーズは「作業エージェント → レビュー担当 → あなたの承認」の順に進みます。

- **レビュー担当**は作業に関わっていない立場で成果物を点検し、根拠を抜き取りで確かめます。問題があれば、あなたに見せる前に作業エージェントに直させます。
- 点検を通ると、オーケストレータが**承認の観点**ごとの確認結果を示して承認を求めます。「要確認」と書かれた観点が、あなたに判断してほしいところです。

### 承認の観点(フェーズごと)

| フェーズ | 観点 |
|---|---|
| 0 | 指示が正しい行に当たっているか / 見つからない・候補が複数ある指示 / 指示の漏れの可能性 / 書式の目印・コメント・図形の扱い / 取り込めなかった情報 |
| 1 | 要件の件数と粒度 / 仮定の正否 / 画面とコードの対応 / 規約・設計方針が実際の書き方と合っているか / 入口の位置 |
| 2 | 変更内容が要件を満たすか / 新規と修正の切り分け / 共通処理の判定漏れ / 規約に沿っているか / 製造順 |
| 3 | 共通処理の全体修正・部分修正の判断 / severity「高」の影響と回帰テスト観点 / 「影響なし」の検索範囲 / フェーズ2との食い違いの解消方法 |
| 4 | 引き継ぎの判定 / 未決事項を残して進めてよいか / タスクの粒度と製造順 / テストの網羅 / 製造フェーズで使う承認の観点 |

### 承認依頼の例(フェーズ1)

```
フェーズ1(読解)が完了し、レビュー担当の点検を通りました(判定: pass_with_notes、軽微な指摘2件)。
レビュー資料: work/runs/20261005-usertel/review/phase1.md

承認の観点:
1. 要件の件数と粒度 … 要確認: T-03 から要件が7件出ています。細かすぎないか見てください(REQ-010〜016)
2. 仮定の正否 … 要確認: ASM-p1a-001「電話番号はハイフンなしで保存」は正しいですか
3. 画面とコードの対応 … 問題なし(SCR-010 → /user/register)
4. 規約・設計方針 … 要確認: Lombok の使い方が混在しています(CNV-014)。新しい機能に合わせて「使う」で読み取っています
5. 入口の位置 … 問題なし

承認して次に進めますか? 差し戻す場合は、観点の番号やIDを添えて理由を教えてください。
```

### フェーズ3: 共通処理の判断の確認
共通処理(他の機能からも呼ばれている処理)に変更が入る場合、1件ずつ確認を求められます。

```
共通処理の判断が1件あります。

CMN-001: CommonValidator#validateTel
- 呼び出し元: 3件(ユーザー登録=今回の対象 / 店舗登録 / 取引先登録)
- 判断: 部分修正(新メソッドを追加し、ユーザー登録だけが使う)。先例: validateZipStrict
- 理由: 店舗登録・取引先登録はハイフンなしの形式を許容しており、全体修正すると既存データが不正になる
- 全体修正した場合の影響: 店舗登録・取引先登録で入力チェックの結果が変わる
- フェーズ2の変更内容(CHG-007)は共通メソッドを直接変更しており、この判断と食い違っています

この判断でよいですか? また、食い違いは次のどちらで解消しますか?
1. フェーズ2をやり直す
2. フェーズ4でこの判断を優先して反映する
```

### 承認する

```
OK
```

### 差し戻す
理由は具体的に書くほど、やり直しの精度が上がります。承認の観点の番号や項目のIDを使うと確実です。

```
差し戻し。
- 観点1: REQ-010〜016 は1つの要件にまとめてよい
- 観点4: Lombok は使わない。既存の書き方に合わせる
```

差し戻した内容に関係するエージェントだけが再実行され、もう一度レビュー担当の点検を経てから承認を求められます。差し戻したフェーズより後ろが承認済みだった場合、それらは「再実行が必要」になり、順にやり直します。

## 4. 仮定と課題への答え方

### 仮定(ASM)
エージェントが置いた解釈です。正しいか誤りかを答えます。

```
ASM-p1a-001 は正しい。ASM-p1a-002 は誤りで、初期値は空欄が正しい
```

### 前のフェーズへの差し戻し候補(ISS)
後のフェーズで、前のフェーズの漏れや誤りが見つかったものです。オーケストレータが次の3択で聞いてきます。

| 選択肢 | 意味 |
|---|---|
| 前のフェーズに戻って再実行 | 前のフェーズを差し戻してやり直す |
| 記録だけして進める | 今回は対応せず、課題として残す |
| 解釈を決める | あなたが決めた解釈を決定事項(DEC)として記録し、先に進める |

あなたの判断は、すべて決定事項(DEC)として記録され、以降のフェーズと製造タスクに反映されます。

## 5. 方針を育てる

やり取りの中で、各フェーズの進め方に改善点が見つかったら、方針として登録し、以降の調査に適用できます。方針は `policies/` に保存され、全エージェントが作業前に読みます。

### 方針の伝え方

```
今後は、ITEM要件は検証ルールごとに分けて
```

```
この設計書の書き方として、赤字は今回の変更、取り消し線は削除、黄色の背景はレビュー中の箇所
```

```
フェーズ3の方針に追加して: バッチから呼ばれている処理は、必ず severity を中以上にする
```

### オーケストレータから提案されることもあります
- 差し戻しのコメントが、今回限りか今後の方針か分からないとき
- 同じ種類の差し戻しやレビュー指摘が繰り返されたとき
- エージェントが手順の改善に気づいたとき

```
「REQは1つの検証ルールごとに分ける」というご指摘は、今後の調査でもフェーズ1の方針にしますか?
方針にする場合の文案:「ITEM要件の validations は、1つの検証ルールごとに別のREQに分ける」
```

文案でよければ「方針にして」、直したければ修正した文を伝えます。

### 進行中の調査への適用
登録した方針が、すでに承認したフェーズにも関係する場合は、そのフェーズからやり直すかを聞かれます。

### 方針の確認・変更・廃止

```
いまの方針を一覧で見せて
POL-phase1-002 を廃止して。理由は〜
```

変更の履歴は `policies/CHANGELOG.md` に残ります。

## 6. 中断と再開

途中でやめても、状態は `work/runs/{run_id}/state.yaml` に残っています。再開するときは、オーケストレータを選んで次のように伝えます。

```
20261005-usertel の続きをやりたい
```

## 7. 成果物と、製造フェーズへの引き継ぎ

```
work/runs/{run_id}/
├─ review/phase0.md 〜 phase4.md      レビュー資料(承認時にまず見るもの。冒頭に承認の観点)
├─ 04_handoff/                        製造フェーズへの引き継ぎ一式
│  ├─ README.md                       製造フェーズの入口(推奨する製造・承認の流れ)
│  ├─ coding_guide.md                 コーディングガイド(現行ソースの規約と手本)
│  ├─ work_plan.yaml                  製造タスク・製造順・確認コマンド・進捗欄
│  ├─ tasks/TSK-001.md …               タスクごとの指示書
│  └─ test_spec.yaml                  テスト仕様(新機能・回帰)
├─ 00_scope/ 〜 03_impacts/           各フェーズの成果物
└─ shared/                            仮定・課題・決定事項の台帳
```

調査の最終成果は `04_handoff/` です。製造フェーズのエージェント(今後作成)は、`04_handoff/README.md` から読み始めます。

タスク指示書には、製造フェーズでエージェント自身が承認フローを回してから利用者に承認を求められるよう、次の観点が含まれます。

| 見出し | 使う場面 |
|---|---|
| 完了条件・検証手順 | 製造担当が実装後に自分で確かめる |
| セルフレビュー観点 | 製造担当が提出前に確かめる |
| 内部レビューの合格基準 | 製造フェーズのレビュー役が合否を判断する |
| 利用者承認の観点 | 内部レビューに合格したタスクを、あなたが承認するときに見る |
| 作業を止めて確認する条件 | 製造担当が途中であなたに確認を求める |

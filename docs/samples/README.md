# 見本

架空のアプリ(Spring Boot + MyBatis + Thymeleaf の「ユーザー登録」)と、架空の設計書で、全フェーズを通しで試したときの資料です。調査ごとに、どんな資料ができるかの見本として見てください。

- 調査: 「ユーザー登録への電話番号認証の追加」
- 指示: 設計書の4シート(画面項目定義・イベント一覧・処理仕様・メッセージ一覧)、見分け方は「変更は赤字、削除は取り消し線」
- 参照用の既存設計書: 会員管理設計書(処理仕様に「既存設計(会員管理設計書 4.2)を参照」とあるため、見出しだけを読んでいます)

## 見どころ

- **シートの変換結果**: 1行 = Excel の1行です。行末の〈 〉に、文字色・取り消し線などの目印が残ります。エージェントはこれを見て、赤字の行(L6・L7)と取り消し線の行(L8)だけを対象にしています。
- **要件の一覧**: 既存の行(L4 氏名、L5 メールアドレス)は要件に入っていません。「必要に応じて再送信できること」は判断に困る表現として、要件にせず確認事項(Q2)にしています。
- **影響調査報告書**: 修正箇所ごとに、ファイル:行と今のコードの抜粋があります。共通処理(CommonValidator)は、呼び出し元を1件ずつ確かめたうえで「部分修正」と判断し、全体修正した場合の影響も書いています。
- **実装計画書**: 「既存の削除(F-03)→ 既存を手本に追加(F-01)→ 新しい仕組み(F-02)」の順です。手順ごとに、直す場所の今のコードと、手本にする既存コードが並びます。手本のない手順(SMS 送信)は確認事項にしています。

コードの抜粋は、すべてスクリプトが実際のソースから切り出したものです(この見本では、架空のアプリのソース)。

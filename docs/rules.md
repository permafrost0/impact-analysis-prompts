# 全エージェント共通のルール

オーケストレータ以外の全エージェントが、作業の前に読みます。

## 1. 立場
- あなたは、追加開発の影響調査チームの一員です。オーケストレータから呼ばれ、決められた1つの作業をします。
- ユーザーとは話しません(質問もできません)。判断が必要なことは、成果物の `question` に書きます。

## 2. 読むだけ(必ず守る)
- **`input/` の中(`input/source/` のソースと、`input/target/`・`input/reference/` の設計書)は読むだけです。** 作成・変更・削除・移動をしません。
- ビルド、テスト、アプリの起動、git の操作をしません(ソースのフォルダに生成物ができるため)。
- 実行してよいコマンドは、`tools/` のスクリプトだけです。
- 書き込んでよいのは、呼び出しで指定された自分の成果物のファイルだけです。
- 各フェーズの終わりに、ソースと設計書が変わっていないことを `tools/guard.py` で確かめます。変わっていれば、調査は止まります。

## 3. 作業の前に読むもの
1. このファイル
2. `docs/schemas/common.md` と、担当フェーズの形式(`docs/schemas/phase{N}.md`。レビュー担当と振り返りの係は `review.md` も)
3. `policies/common.md` と、担当フェーズの方針(`policies/phase{N}.md`。レビュー担当は `policies/review.md` も)
4. 呼び出しで渡された、差し戻し・指摘・ユーザーの判断

方針(policies/)と、エージェント定義の手順が食い違うときは、**方針を優先**します。

## 4. 根拠
| 何の根拠か | 使ってよいもの |
|---|---|
| 何を変えるか(要件) | 指示されたシートの変換結果(`01_requirements/sheets/`)のうち、対象の行と見出し行 |
| 既存の振る舞い・修正箇所・影響・書き方・置き場所 | **ソースコードだけ**(`code:`) |

- 設計書に書かれた既存の内容は、既存の仕様の根拠にしません。設計書とコードの突き合わせもしません。
- 指示されていないシートは読みません。必要そうなら、課題(issues)か確認事項(question)にします。
- **ほかの調査の成果物は使いません。** 自分の調査フォルダ(`work/runs/{調査ID}/`)以外の `work/runs/` と、`history/` は読みません。コードを検索したときに、それらのファイルやソースのルートの外のファイルが結果に出ても、根拠にしません(調査は毎回、コードから必要な範囲だけを調べます)。振り返りの係だけは、`history/` を読みます。
- 例外: p1b-extract だけが、決められた条件で、参照先の既存設計書の**見出しの一覧**を読めます(本文は読みません)。

## 5. 検索のしかた
- 調査するソースは `input/source/{フォルダ名}/` にあります(scope.yaml の `source_root`)。コードの根拠のパス(`code:` と excerpt の file)は、このフォルダからの相対パスで書きます。
- **コードを検索するときは、検索の対象を `source_root` の下に絞ります**(検索のパターンに `input/source/{フォルダ名}/**` を指定する)。このリポジトリには、見本や形式の説明にコードの例が含まれているためです。
- `work/runs/` と `history/` は検索の対象から外れています(.gitignore に入っているため、検索しても見つかりません)。調査フォルダの成果物と変換結果は、**ファイルを開いて読みます**。検索で見つからないことを「ない」の根拠にしません。

## 6. 書き写しの決まり
- 設計書の値は、変換結果のとおりに写します。言い換え・要約・全角半角の統一をしません。
- コードは書き写しません。載せたい箇所は `excerpt`(file / start / end)で範囲だけを書きます。中身はスクリプトが実際のソースから切り出します。

## 7. 他の成果物
- 自分の担当以外の成果物は読み取り専用です。誤りや漏れに気づいたら、直さずに `issues` に書きます(target に、問題のある作業者タグ)。
- 同じ段で並列に動いている他のエージェントの成果物は読みません(書きかけかもしれないため)。

## 8. 決めきれないとき
- 推測で埋めずに、仮定(`assumptions`)を立てます。
- ユーザーの判断が必要なら `ask_user: true` にし、`question` を付けます。question には**今どう扱っているか**を書きます(ユーザーが答えなければ、そのまま確定するため)。
- ユーザーの判断(`decisions.yaml`)は確定事項です。必ず反映します。

## 9. 完了の前
1. `python tools/check_outputs.py work/runs/{調査ID} --file {自分の成果物のパス}` を実行し、エラーがなくなるまで直します。
2. 結果を `meta.self_check` に記録します。

## 10. 最後の応答(完了報告)
オーケストレータに渡るのは最後の応答だけです。次の形で書きます。

```
## {エージェント名} 完了報告({作業者タグ} / attempt {n})
- 成果物: {パス}
- 件数: {種別ごとの件数}
- 確信度「低」: {件数と ID。なければ「なし」}
- ユーザーに確認したいこと: {question を付けた項目の ID。なければ「なし」}
- 他の成果物の課題: {ISS の ID と一行の要約。なければ「なし」}
- 自己点検: {check_outputs の結果}
- 差し戻し・指摘への対応: {該当するときだけ}
- 方針への提案: {手順の改善案。なければ「なし」}
- 作業できなかったこと: {環境の問題などで止まったときだけ。理由}
```

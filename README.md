# 追加開発の影響調査エージェント(GitHub Copilot 用)

追加開発の**設計書(Excel)**と**既存のソースコード**から、次の2つを作る GitHub Copilot(VS Code)のカスタムエージェント一式です。

| 最終成果物 | 中身 | 使いみち |
|---|---|---|
| **影響調査報告書**<br>`02_impact/impact_report.md` | 機能ごとの修正箇所(ファイル:行とコードの抜粋)、既存機能への影響、実装上の懸念 | 既存への影響と懸念の把握 |
| **実装計画書**<br>`03_plan/implementation_plan.md` | 作る順番、機能ごとの作業手順(直す行と今のコード、手本にする既存コードつき)、確認方法 | **製造工程の入力** |

あなたが話す相手は **`impact-orchestrator`(オーケストレータ)だけ**です。オーケストレータが、作業の担当エージェントとレビュー担当を順に呼び出し、フェーズの区切りごとにあなたの承認を求めます。

---

## 1. 全体の流れ

```
あなた:「新しい調査を始めたい」
  │
  ▼
準備 ……… シート名の確認 → ソースと設計書の状態を記録 → 指示したシートだけを Markdown に変換
  │
  ▼
フェーズ1 要件の抽出 ……… 設計書から「今回、何が変わるか」を取り出し、機能ごとにまとめる
  │   レビュー担当の点検 → ★あなたの承認(要件の一覧)
  ▼
フェーズ2 懸念事項の抽出 … ソースを調べ、修正箇所・既存機能への影響・実装上の懸念を出す
  │   レビュー担当の点検 → ★あなたの承認(影響調査報告書)
  ▼
フェーズ3 実装計画 ……… 作る順番と、機能ごとの作業手順・確認方法を決める
  │   レビュー担当の点検 → ★あなたの承認(実装計画書)
  ▼
振り返り ……… 今回の差し戻し・指摘から、次回のための方針の改善案を出す
      → あなたが採用したものだけが、次の調査から使われる
```

- **承認は3回**(フェーズごとに1回)です。あなたが開くファイルは、毎回1つだけです。
- 各フェーズの最後には、作業に関わっていない**レビュー担当**が点検します。問題があれば、あなたに見せる前に直させます。
- フェーズの途中であなたに質問が来るのは、次のときだけです。
  - 指示した部分が設計書のどこか決められない、または指示していないシートを参照している(フェーズ1の途中)
  - レビュー担当の不合格や点検のエラーが、2回直しても解消しない
  - 承認済みのフェーズに誤りが見つかり、戻るかを決める必要がある
  - ソースや設計書が変わったことを検知した、または Python が使えないなど環境の問題がある

---

## 2. はじめての準備

詳しくは [docs/usage.md](docs/usage.md) を見てください。

1. **必要なもの**: VS Code、GitHub Copilot(Copilot Chat のエージェントが使えること)、Python 3.8 以上
   (Excel を読むライブラリ openpyxl と pyyaml は、足りなければオーケストレータが入れます)
2. **ソースと設計書を置く**(どれも、このフォルダの `input/` の下です)
   - `input/source/{フォルダ名}/` … 調査する**既存のソース**(例: `input/source/myapp/`。フォルダごとコピーする)
   - `input/target/` … 今回の**追加開発の設計書**
   - `input/reference/` … 追加開発の設計書から参照されている**既存の設計書**(あれば。必要なときに見出しだけが読まれます)
3. VS Code で**このフォルダを開きます**(ほかのフォルダを追加する必要はありません)
4. Copilot Chat のエージェント選択で **`impact-orchestrator`** を選びます

---

## 3. 調査の始め方

必ず伝えるのは、**シート名**と**追加開発の部分の見分け方**だけです。パスや行番号を書く必要はありません。

```
新しい調査を始めたい。
シート: 画面項目定義、イベント一覧、処理仕様、メッセージ一覧
見分け方: 変更は赤字、削除は取り消し線
```

- 設計書は `input/target/` に、ソースは `input/source/` に1つずつ置かれていれば、それが使われます。複数置いているときは、どれを使うかを名前で聞かれます(「ソース: myapp」のように先に伝えても構いません)。
- 調査の名前は、言わなければ自動で付きます。

見分け方は、次のどれでも構いません(組み合わせても構いません)。

| 見分け方 | 例 |
|---|---|
| 書式の目印 | 「変更は赤字」「削除は取り消し線」 |
| 名前 | 「イベント一覧の『電話番号認証ボタン押下』を追加」 |
| シート全体 | 「メッセージ一覧は全部が新規」 |

「赤字は変更」のような**いつも同じ決まり**は、方針として登録できます。登録すると、次からはシート名を伝えるだけで済みます。

---

## 4. 承認のしかた

フェーズが終わると、オーケストレータから次の形で依頼が来ます。

```
開くファイル: work/runs/20261007-usertel/01_requirements/requirements.md

フェーズ1(要件の抽出)が終わりました。レビュー担当の点検: 条件付き合格
3つの機能(電話番号の入力・電話番号の認証・FAX番号の廃止)、7件の要件を抽出しました。
判断に困る表現が1件、仮定が1件、参照先から特定した流用先が1件あり、確認事項にしています。

確認事項が 3 件あります(資料の「2. 確認事項」)。
番号を付けて答えてください。例:「Q1: はい / Q2: ハイフンあり」
答えなかった確認事項は、資料に書かれている内容のまま確定します。
内容に問題がなければ「承認」、直してほしい点があれば具体的に伝えてください。
```

依頼の1行目は、いつも「開くファイル」です。承認資料は、どのフェーズも同じ並びです。

1. **はじめに** … レビュー担当の要約
2. **1. 機能ごとの内容** … まずここで、取り出された内容そのものを確かめます(フェーズ1は「抽出した要件」、フェーズ2は「抽出した内容」、フェーズ3は「実装計画」)
3. **2. 確認事項** … Q1, Q2, … の番号つき。**答えなかったものは、資料に書かれた内容のまま確定**します
4. **付録** … レビュー担当の点検結果、仮定と課題の一覧など

あなたの答えはオーケストレータが記録し、内容を変える答えや修正の指示があれば、該当の担当エージェントに直させてから、もう一度承認を求めます。

---

## 5. できあがるもの

調査ごとに `work/runs/{調査ID}/` に作られます(調査ID は `20261007-usertel` のような形)。

| ファイル | いつ | 中身 |
|---|---|---|
| `01_requirements/requirements.md` | フェーズ1 | 機能ごとの要件(新規・変更・削除・既存の流用)と、設計書の箇所 |
| `02_impact/impact_report.md` | フェーズ2 | **影響調査報告書**。機能ごとに、今の処理の流れ → 修正箇所(コードの抜粋つき)→ 流用する既存処理 → 既存機能への影響 → 実装上の懸念 → 調べた範囲 |
| `03_plan/implementation_plan.md` | フェーズ3 | **実装計画書**。実装の順番と、機能ごとのゴール・作業手順(直す行と今のコード、手本のコードつき)・新しく作るもの・合わせる書き方・守るべき既存の振る舞い・確認方法・完了条件 |
| `retrospective.md` | 振り返り | 今回の気づきと、方針の改善案 |

見本は [docs/samples/](docs/samples/) にあります(架空のアプリで試したもの)。

`.md` の資料は、エージェント同士がやり取りする YAML ファイル(正本)からスクリプトが作ります。コードの抜粋も、スクリプトが実際のソースから切り出すので、書き写しの誤りが入りません。資料を手で直す必要はありません。直したい点はオーケストレータに伝えてください。

## 6. 構成

### 6-1. エージェント

| フェーズ | 段 | エージェント | 何をするか | 同時に動く数 |
|---|---|---|---|---|
| - | - | **impact-orchestrator** | あなたとの窓口。呼び出しの順番・点検・承認・記録を受け持つ(自分では調査しない) | - |
| 1 要件の抽出 | 1 | impact-p1a-scope | あなたの指示(赤字、名前など)を、シートの具体的な行に当てはめる | 1 |
| | 2 | impact-p1b-extract | 1シート分の対象の行から要件を取り出し、新規・変更・削除・既存の流用に分ける | シートごと(最大3) |
| | 3 | impact-p1c-integrate | 要件を利用者から見た機能(F-01 など)にまとめる | 1 |
| 2 懸念事項の抽出 | 1 | impact-p2a-reuse | 「既存の○○と同様」とされた流用先を、コードから特定する | p2b と合わせて最大3 |
| | 1 | impact-p2b-changes | 1機能分の処理の流れをコードで辿り、修正箇所を決める | 機能ごと |
| | 2 | impact-p2c-impacts | 修正が既存機能に与える影響を調べる | 3つ同時 |
| | 2 | impact-p2d-common | 共通処理を全体修正にするか部分修正にするかを、呼び出し元ごとに判断する | |
| | 2 | impact-p2e-concerns | 作るうえでの危うさ(トランザクション、既存データなど)を出す | |
| 3 実装計画 | 1 | impact-p3a-plan | 機能を作る順番を決める | 1 |
| | 2 | impact-p3b-steps | 1機能分の作業手順を、手本の既存コードとあわせて書く | p3c と合わせて最大3 |
| | 2 | impact-p3c-verification | 要件の確認方法と、既存機能の回帰の確認方法を決める | |
| 点検 | - | impact-reviewer | 作業に関わっていない立場で成果物を点検し、合格・条件付き合格・不合格を出す | - |
| 振り返り | - | impact-retrospective | 差し戻し・指摘・確認事項から、方針の改善案を作る | - |

- 1つのエージェントは1つの作業だけを受け持ちます。
- **前の段の成果物を使うときだけ順番に**動かし、それ以外は並列に動かします(同時に最大3つ)。

### 6-2. レビュー担当の点検(5か所)

| 点検 | いつ | 主に見ること | その後 |
|---|---|---|---|
| p1-scope | p1a の後(フェーズ1の途中) | 範囲が指示どおりか。既存の行が混ざっていないか | 合格なら抽出へ |
| p1 | フェーズ1の最後 | 要件の値が設計書どおりか、区分が正しいか、既存の記述が混ざっていないか | あなたの承認へ |
| p2-changes | p2a・p2b の後(フェーズ2の途中) | 修正箇所の「今の振る舞い」がコードどおりか、修正の漏れ、共通処理の判定漏れ | 合格なら影響調査へ |
| p2 | フェーズ2の最後 | 影響・懸念の根拠がコードか、並列で調べた結果の食い違い | あなたの承認へ |
| p3 | フェーズ3の最後 | 順番、手本の実在、新しく作るものの名前・置き場所、判断の反映 | あなたの承認へ |

途中の点検(p1-scope、p2-changes)はエージェントだけで行い、あなたへの承認依頼はありません。後の作業が誤った前提で進むのを防ぐためのものです。
どの点検でも、先にスクリプト(`tools/check_outputs.py`)が形式・根拠の実在・漏れを機械的に確かめ、そのうえでレビュー担当が根拠を実際に開いて確かめます。

### 6-3. スクリプト(`tools/`)

| スクリプト | 役割 |
|---|---|
| `convert_sheets.py` | 指示されたシートだけを、1行=1行の Markdown に変換する(文字色・取り消し線・結合・コメント・図形の文字も残す) |
| `list_headings.py` | 参照先の既存設計書の**見出しだけ**を出す(本文は出さない) |
| `guard.py` | 調査の開始時にソースと設計書の状態を記録し、各フェーズの最後に変わっていないことを確かめる(IDE やビルド、Excel が自動で作るファイルは照合から外す) |
| `check_outputs.py` | 成果物の形式・根拠の実在・漏れ・ID の重なりなどを機械的に点検する |
| `render_docs.py` | YAML から承認資料(`.md`)を作る。コードの抜粋を実際のソースから差し込み、確認事項に Q 番号を振る |

すべて読むだけのスクリプトで、ソースや設計書を書き換えません。

### 6-4. フォルダ

```
(このフォルダ)
├─ README.md                    この文書
├─ .github/
│  ├─ copilot-instructions.md   ワークスペース全体の決まり
│  └─ agents/                   エージェントの定義(14個)
├─ docs/
│  ├─ usage.md                  使い方の詳細
│  ├─ rules.md                  全エージェント共通のルール
│  ├─ schemas/                  成果物(YAML)の形式
│  └─ samples/                  承認資料の見本
├─ policies/                    方針(振り返りで採用した改善。次の調査から使われる)
├─ tools/                       スクリプト
├─ input/                      調査に使うもの(すべて読むだけ)
│  ├─ source/{フォルダ名}/      調査する既存のソースを置く(例: input/source/myapp/)
│  ├─ target/                   追加開発の設計書を置く
│  └─ reference/                参照用の既存設計書を置く(必要なときに見出しだけ読まれる)
├─ work/runs/{調査ID}/          調査ごとの作業フォルダと成果物
└─ history/                     調査・差し戻し・確認事項の記録(振り返りで使う)
```

`input/`、`work/runs/`、`history/` の中身は、各自の PC の中だけで使います。`input/target/`・`input/reference/`・`work/runs/`・`history/` は git の管理対象外にしています。`input/source/` だけは、エージェントがソースを検索できるよう、あえて対象外にしていません(.gitignore に入れると、Copilot の検索の対象から外れるため)。このフォルダを git で管理している場合は、`input/source/` の中身をコミットしないでください。

---

## 7. 守っていること

| 決まり | 理由 |
|---|---|
| **`input/` の中(ソースと設計書)は、すべてのフェーズで読むだけ**。各フェーズの最後に、変わっていないことをスクリプトで確かめる | 調査が対象を壊さないように |
| **既存の仕様は、ソースコードだけを根拠にする**。設計書に書かれた既存の内容は使わず、突き合わせもしない | 設計書は実装と食い違っていることがあるため |
| 設計書から読むのは、**指示されたシートの、対象の行と見出し行だけ** | 既存の記述が要件に混ざらないように |
| 参照先の既存設計書は、追加開発の設計書に参照が明記され、かつ機能を特定できないときだけ、フェーズ1で**見出しだけ**読む | 「どの既存機能か」を知るためだけに使い、仕様の根拠にしない |
| 「必要に応じて」「従来どおり」など判断に困る表現は、要件にせず**確認事項**にする | 推測で要件を作らないように |
| 設計書の値は一字一句そのまま写し、コードは書き写さずにスクリプトが切り出す | 写し間違いを防ぐため |
| 調査は毎回、必要な範囲だけをコードから調べる(ほかの調査の成果物は使わない) | 古い調査結果に引きずられないように |

## 8. 使うほど良くなる仕組み

```
調査中: あなたの修正・差し戻し・レビュー担当の不合格 ──▶ history/feedback_log.md に記録
        確認事項とあなたの答え(答えなかったものも) ───▶ history/questions_log.md に記録
                                                           │
フェーズ3の承認の後: 振り返り(毎回) ◀─────────────────────┘
  │  今回の記録と過去の記録を見て、方針の改善案(P1, P2, …)を出す
  ▼
あなた:「P1: 採用 / P2: 不採用」
  │
  ▼
policies/ に追記(変更の履歴は policies/CHANGELOG.md)──▶ 次の調査から全エージェントが従う
```

- 改善案は、エージェントの手順を直すもの(`policies/phase1.md` など)と、レビュー担当の点検項目を足すもの(`policies/review.md`)があります。
- 調査中に「今後は〜」と伝えた決まりも、その場で方針に登録するかを聞かれます。
- 答えなかった改善案は採用されません(確認事項とは扱いが逆です)。
- 方針は、エージェント定義の手順より優先されます。方針が増えすぎないよう、重なるものは書き直し・廃止も提案されます。
- `history/` は各自の PC の中だけで使います(git の管理対象外)。`policies/` は git の管理対象ですが、各自の PC で育っていきます。チームで揃えたいときは、`policies/` のファイルを共有してください。
